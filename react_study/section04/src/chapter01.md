## React.js

: Meta가 개발한 오픈소스 JS 라이브러리

- 대규모 웹서비스의 **UI를 좀 더 편하고 빠르게** 개발할 수 있다.
- 넷플릭스, 페이스북, 인스타, 노션 등
- 가장 인기가 많음. 2등인 Vue.js와는 2배 차이



### React의 기술적인 특징

## 1. 컴포넌트를 기반으로 UI를 표현한다.

- 웹페이지가 Header, Main, Footer로 나뉘면 리액트는 header.js, main.js, footer.js라는 각각의 JS 파일로, 즉 component라는 단위로 나눠서 모듈화해서 보관할 수 있기 때문에, 웹페이지를 마치 레고를 조립하듯이 여러 개의 컴포넌트들을 합쳐서 만들어낼 수 있다.
  - –> **중복 코드를 제거할 수 있다!**
  - 만약 비슷한 두 페이지를 개발한다고 하면 컴포넌트를 이용하지 않을 때는 공통 헤더가 있을 때 일일이 이 헤더를 사용하는 모든 페이지에 **HTML로 직접 헤더를 마크업(UI 구현) 해줘야 한다.**
  - 이러면 중복 코드가 발생하고, 그렇게 되면 가벼운 수정 사항에도 바꿔줘야 할 코드들이 여러 파일에 산재하기에 페이지 숫자가 늘어나면 **코드를 유지보수하기 어려워진다.**
    - **리액트**는 컴포넌트라는 단위로 **모듈화**해서 개발하기 때문에 **그 컴포넌트만 수정하면 돼서** 이걸 예방할 수 있다!





## 2. 화면 업데이트 구현이 쉽다.

* **업데이트** : 버튼을 클릭했을 때 버튼의 모양이 변화하는 것처럼 사용자의 클릭이나 드래그 같은 행동에 따라서 웹페이지가 스스로 자신의 모습을 바꿔 사용자와 상호작용하는 모든 기능들

##### 리액트는 선언형 프로그래밍이라서 화면 업데이트 구현이 쉽다!

- **선언형 프로그래밍** : 불필요한 과정은 생략하고 이루고자 하는 목적만 간결히 명시하는 방법
  - "토마토 파스타 주세요."
  - 코드가 간결함 –> 리액트
- **명령형 프로그래밍** : 목적을 이루기 위한 모든 일련의 과정을 설명하는 방식
  - "우선 주방으로 가셔서 면 100g을 꺼내세요, 그리고 뜨거운 물에 9분간 삶으세요 그런 다음 후라이팬을 꺼내 불을 올리고 …"
  - 코드가 복잡함 –> JS

##### 각각의 컴퍼넌트에는 현재 컴퍼넌트의 상태를 저장하는`state`가 있다. #####

- state의 값이 바뀌면 컴퍼넌트가 바뀐 스테이트 값에 따라서 각각 다른 UI를 화면에 렌더링하도록 설정할 수 있다.
  - **렌더링** : 웹페이지에 UI 요소를 화면에 그려내는 것

- 만약, state 변수의 값이 1이면 렌더링 결과가 1번 UI, 2면 2  –> 편하고 간결하게 업데이트를 구현



##### 리액트는 업데이트를 위한 여러가지 복잡한 동작들을 명령형 방식으로 직접 정의할 필요가 없이, 그냥 특정 변수의 값만 바꿔주면 선언형 방식으로 해당 변수의 값에 따라서 화면이 업데이트 되도록 처리할 수 있다.



## 3. 화면 업데이트가 빠르게 처리된다.

- **브라우저 렌더링 과정**(`Critical Rendering Path`)이 있음.
  - JS -> HTML -> DOM**(document object model)** -> Render Tree -> Layout -> Painting
  - CSS -> CSSOM**(css object model)** -> Render Tree -> Layout -> Painting
- **DOM** : HTML의 코드를 브라우저가 이해하기 쉬운 객체 형식으로 변환한 문서 객체 모델

- **CSSOM** : CSS로 표현한 요소들의 스타일과 관련된 모든 정보가 있음.

- **Render Tree** : 웹페이지의 설계도 역할. DOM과 CSSOM을 합쳐서 만든 렌더 트리에는 화면에 렌더링되어야 하는 요소들의 모든 정보가 다 포함되어야 한다.

- **Layout** : 요소의 배치를 잡는 작업

- **Painting** : 실제로 화면에 그려내는 과정



##### 화면의 업데이트는 어떻게 이루어질까?

: <u>JS가 DOM을 수정하게 되면 발생</u>한다.

DOM이 수정되면 브라우저는 이 브라우저 렌더링 과정을 **<u>전체 단계를 다시 진행</u>**한다.

그래서 **렌더 트리를 다시 생성**하고 <u>**레이아웃**을 다시 잡고</u> <u>**페인팅**을 다시 진행</u>한다.

그럼으로써 화면에 그려지는, 즉 렌더링되는 요소가 변경이 되면서 업데이트가 실제로 이루어진다.



##### 주의해야 할 사실

브라우저 렌더링 과정 중에 3단계 Layout과 4단계 Painting은 다시 하는 걸 따로 부르는 이름이 있을 정도로 꽤나 오래 걸리는 작업.

- DOM이 수정되어서 레이아웃이 다시 진행되는 것 == Reflow
- DOM이 수정되어서 페인팅이 다시 진행되는 것 == Repaint

수정이 많이 되면 심할 경우 브라우저에서 ''응답 없음'' 페이지가 뜨면서 마비가 되어버리는 현상이 발생할 수도 있다.

```html
<script>
    function onClick(){
        const $ul = document.getElementById("ul");
        for (let i = 0; i < 3000; i++){
            $ul.innerHTML += `<li>${i}</li>`;
        }
    }
</script>
<body>
    <button onClick="onClick()">리스트 추가하기</button>
    <ul id="ul"></ul>
</body>
```

🤔 **나쁜 예시**

- 3,000번의 DOM을 수정
- 성능 측정 결과 : 4,500ms



```html
<script>
    function onClick(){
        const $ul = document.getElementById("ul");
        let list = "";

        for (let i = 0; i < 3000; i++){
            list += `<li>${i}</li>`;
        }

        $ul.innerHTML= list;
    }
</script>
<body>
    <button onClick="onClick()">리스트 추가하기</button>
    <ul id="ul"></ul>
</body>
```

✨ **좋은 예시**

- DOM은 딱 한 번만 수정함
- 성능 측정 결과 : 250ms (약 22배 개선 됨)

–> 2줄만 수정하니까 이전에 비해 20배 빠르게 성능이 개선됨.



##### 결론

JS로 DOM을 직접 수정해서 업데이트를 구현할 때에는 DOM 수정 횟수를 최소화해야 하기 때문에.

동시에 발생하는 다양한 업데이트들이 있을 때 업데이트들이 하나씩 다 DOM을 수정시키도록 만드는 게 아니라(성능 구려짐) 변수 등 같은 장소에 업데이트들을 다 모아두었다가 한 번만 DOM을 수정할 수 있도록 각별히 신경을 써주자!

##### 어? 근데 리액트는 자동으로 해줍니다.

동시에 발생한 업데이트들을 모아서 DOM 수정 횟수를 최소화하는 작업을 리액트에서는 자동 처리

### 어떻게? 가상 DOM

: 내부적으로 가상 DOM이라는 가상의 DOM을 이용하고 있음.

**Virtual DOM**이란

- 실제 브라우저가 렌더링하는 DOM을 JS 객체로 카피해놓은 것
- 그래서 리액트에서는 가상 DOM을 이용해서 업데이트가 발생하면 실제 DOM을 바로 수정하는 게 아니라, 가상 DOM을 먼저 수정하도록 만든다.
- 업데이트가 생기면 가상 DOM에 모아서 반영함. 다 모으면 실제 DOM에 반영.
  - **가상 DOM이 일종의 버퍼 역할**, 즉 업데이트들을 모아두는 장소 역할을 해서 동시에 아무리 많은 수의 업데이트가 발생한다고 하더라도 최소한의 횟수로 DOM이 수정된다.
  - 따라서, **리액트는 좋은 업데이트 성능을 보장**해준다.
